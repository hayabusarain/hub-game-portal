## 3. 根拠の整理

### 公式に書かれていること（11/7 取得）

- 資格要件に、流入・運営期間・ページ数・登録数の数値の基準は無い（answer/9724・81904）。「ウェブ上で一貫したプレゼンス」「ユーザーの関心」を定義した公式のページも見つからない。10/30 の文面は、9月中旬から全体に配られている定型文だった
- answer/10015918 は、独自の価値のうち最も重要なものとして「専門家の知識、何かを改善する方法、クチコミ情報、自分のアイデア」を挙げる。似たページは充実させるか統合し、同じ文を複数のページに置かず、長い注意書きは概要とリンクにするよう求めている
- 同じページは、Google ウェブ検索のスパムポリシーに従うことも求めている。スパムポリシーには、付加価値なしに生成 AI で大量のページを作ること（scaled content abuse）と、検索結果に近い似たページ（doorway）が載っている
- publisherpolicies/11112688 は、ナビゲーションや操作のための画面と、手動のレビューやキュレーションが無い自動生成の画面に広告を置かないよう定めている
- AdSense のクローラーは広告タグのある URL を読み、反映に最長1〜2週間かかる（answer/99376）。管理画面でサイトを削除して出し直すと、審査が遅れる（12170222）。再申請までの待ち期間はあるが、日数は書かれていない（7003627）

Diamond Product Expert のガイド（community-guide/241032356）は、匿名のサイトと中核を AI で作ったサイトは落ちやすいと書く。公式の文書ではない。

### 競合との差

比べた個人の攻略サイトの多くは、ハンドル名か書き手の名前を出していた。到達ランクまで出していたのは2つ（ふみばら・ややや）だけだ。
運営者の情報がほとんど無いのに、pub ID が sellers.json に載っているサイトもあった。当サイトは、屋号のほかに書き手の情報を出していない。
広告コードのある個人サイトの初出は、2019〜2024年だった。HoK だけを扱う2026年開設の個人サイトで、広告が出ている例は無かった。
広告コードがあっても、そのサイトが審査を通ったとは限らない。承認がアカウントの単位でずっと前に済んでいた見込みもある（推測）。
一覧が個別ページの全文を抱える作りは、競合には無かった。更新の頻度、出典と取得日の書き方、ヒーロー記事の分析は、当サイトが劣っていない。

- 注意: 開示は 9/8 と 10/30 のときにもあって落ちている。戻すだけでは、落ちたときの状態に戻るにとどまる。正直に書くと「手動のレビューの無い自動生成」と読まれるおそれもあるので、B2 と組にして出す
- 誰が: 運営者（案文の選択と事実）→ ポータル・HoK・MLBB のセッション

**B2　流入の多いページに、運営者が確かめたことを足す（11/7 に運営者が「使っているヒーローは出せない」と答えたので、やらない）**

- どこへ: ポータルのセッションがクリック上位から20体ほどの候補を出し、運営者が実際に使っているものから5〜10体を選ぶ（HoK・MLBB）。HoK の Tier 表の下も対象にする（表より上には足さない）

- 置き場所: MLBB では、運営者のメモを heroStrategy に混ぜない（根拠をスキル本文とバトルプランに限る決まりで、検査22が見ている）。`src/content/` の新しいファイルに置く。HoK も MLBB も、出所表に1行足す
- MLBB の決まり: 「実機で確かめた」の語、確認日、自分の画面の写真をページに出すと、9/5 の指示（工程は書かない、出す日付は最終更新日だけ）に当たる。運営者が緩めるかを決める
- HoK の英語版: メモの事実は英語版にも載せる。英文を AI が書くことは、B1 の開示に入れる

- あわせて: 選んだページに残る AI の文の型を、手で崩す。MLBB は133本中約60本が「中盤以降の○○は」で始まる（11/7、ソースで60・本番で58）。HoK の strategy には「絶対」11・「鉄則」16・「正解」18・「溶け」10・「一瞬で」10・「消し飛」5 などがある（11/7、「必ず」49を含めて計121）。一括では取り直さない

**B3　ゲーム内で画面を見れば分かる「未確認」を片づける**

**運営者の事実が間に合わない、または出せない場合**

- **中身を変えずに試しの申請をしない。** 俗説（ページ数・字数・1日100PV・「6か月待て」）も申請の条件にしない

## 6. 出し方と確かめ方

各セッションは、着手の前に項目ごとのおおよその作業量を出す。Claude の使用枠が足りないときは、C から削る。
サブエージェントを4本以上回す作業は、本数と目的を先に出して運営者の承認を取る（共通ルール1）。待つ期間に許す HoK の統計の取り込みも、講評の書き直しに6本要るのでこれに当たる。

push はリポジトリごとに1〜2回にまとめる。手元で tsc・eslint・audit・build と画面を確かめてから、まとめて運営者の承認をもらう。
出す前に、`/hok/ja/tier-list` と `/mlbb/ja/tier-list` の HTML を保存しておく。

出したあとは、push ごとに次を確かめる。
- curl で: 「0体は」が0件、/patches の `<main>`（script を除く）に過去の版の本文が無い。C1 を出したときは、`/mlbb/ja/heroes/lane/*` が 301 で `/mlbb/ja/tier-list/*` に着き、サイトマップに heroes/lane が無い
- `/hok/en` の変えたページで、日本語の字数が0（英語名が未確認のスキン名「百花繚乱」だけは例外）
- Tier 表2本の表より上が、保存した HTML と同じ（統計の値を除く）
- 375px の幅で、フッターと最下部がタブバーに隠れていない

push から7日間は、ポータルのセッションが Search Console で Tier 表2本のクリックと順位を見る。
戻す線は、出す前に運営者と数値で決める。案は「自分の push のあと3日続けて、前の週の同じ曜日より3割以上落ちたら、戻すかを相談する」。
各 push のコミットと日付は審査記録に書く。最後の構成の push には「14日の起点」と書き添える。
